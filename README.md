# PacRunner

PacRunner is a compiler to convert [pyAmpliCol](https://github.com/MadGraphTeam/pyamplicol)'s recurrence 
mode processes to UMAMI-compatible libraries for both CPU and GPU.

Unified  MAtrix  eleMent  Interface (UMAMI) is a standard interface to bridge various matrix elements 
generators and [MadGraph](https://github.com/MadGraphTeam/MadGraph7) ecosystem. 

## Installation

1. Clone [MadGraph7](https://github.com/MadGraphTeam/MadGraph7/):
   `git clone https://github.com/MadGraphTeam/MadGraph7.git`. 
2. Build MadSpace and pyAmpliCol inside the checkout, either from the MadGraph7 prompt
   (`./bin/madgraph`, then `install madspace` and `install pyamplicol`) or from the checkout's root:
   ```sh
   python madspace/install.py --source -y
   python pyamplicol/install.py --source -y
   ```
   Do not pass `--system`: the builds go to `madspace/install` and `pyamplicol/install`.
3. Optional, for `device="cuda_full"` (MadSpace itself on the GPU): a CUDA build of MadSpace in
   `madspace/install-cuda`, next to the CPU build of step 2 (whose build dependencies it uses):
   ```sh
   cd madspace
   PYTHONPATH=install python -m pip install --no-build-isolation --upgrade \
       -Cbuild-dir=build-cuda --target=install-cuda \
       -Ccmake.define.ENABLE_CUDA=ON -Ccmake.define.CMAKE_CUDA_ARCHITECTURES=120 \
       -Ccmake.define.ENABLE_OPENBLAS=ON -Ccmake.build-type=Release .
   ```
   `device="cuda"` does not need it (the matrix elements on the GPU, MadSpace on the CPU).
4. Optionally, install symjit 2.29 or later from conda-forge: `conda install -c conda-forge 'symjit>=2.29'`.
   symjit is a pip requirement of PacRunner (`symjit>=2.29`): step 6 keeps a conda symjit that
   satisfies it, and otherwise installs symjit from PyPI.
5. Clone PacRunner: `git clone https://github.com/shahriariravanian/pacrunner`, then `cd pacrunner`.
6. Install it, editable: `python -m pip install -e .` (a plain `python -m pip install .` works too: the C
   sources, `pacrunner/c/`, are package data; editable is for working on PacRunner).
7. Point PacRunner at the MadGraph7 checkout: `export PACRUNNER_MADGRAPH7=/path/to/MadGraph7`, or
   `pacrunner.configure(madgraph7="/path/to/MadGraph7")` before the first runtime. PacRunner then
   imports MadSpace from `madspace/install-cuda` when it exists and from `madspace/install` otherwise
   (`configure(cuda=False)`: the CPU build), and finds pyAmpliCol in `pyamplicol/install`. Do not put
   these folders on `PYTHONPATH`: a MadSpace imported before PacRunner chooses its build cannot be
   switched (`configure` then fails with "MadSpace is already loaded in this process"). Without
   either setting, PacRunner uses the MadGraph7 an mg7 output was made with, or a `madspace`
   installed in the python.
8. Optional tests: `python -m unittest discover -s test/python` (see [Tests](#tests)).
9. Set `export NVCC=path/to/nvcc` (optional, should be needed only if CUDA is installed in a non-standard location).

You also need a C compiler (`cc`, or `CC`), and `nvcc` for the GPU devices.
  
## Quick Start

Before explaining how PacRunner works, let's run a simple example showcasing the interaction 
between pyAmpliCol and MadGraph. 

Start in a scratch folder. First, we generate a process by running

```
pyamplicol generate "u u~ > z g g" artifacts/zgg --color-accuracy lc --emit-api-bundle
```

Now, `artifacts/zgg` is the artifact folder generated by pyAmpliCol for the "u u~ > z g g" process.
In addition, `artifacts/zgg/API/umami/` contains the source for the UMAMI wrapper. However, it is not 
compiled yet. You can compile it as `make -C artifacts/zgg/API/umami/`, but PacRunner will compile it 
on demand if not available. After this command is executed, the compiled UMAMI driver (`libumami.so` 
or `libumami.dylib`) is placed in `artifacts/.pyamplicol-api-build/zgg/umami/`. 

First, let's see how PacRunner's Python API works. The first example does not use PacRunner's
compiler and runs the stock matrix-element generator:

```python
import pacrunner

a = pacrunner.Artifact("artifacts/zgg/")    # a pyAmpliCol artifact
process, momenta = a.validation_points()[0]
batch = momenta[None, :, :]                 # a batch of one event
provider_stock = a.stock()                  # pyAmpliCol's own provider (libumami.so beside the artifact)
rt_stock = provider_stock.runtime()         # a pacrunner.Runtime of its channel 0
print(rt_stock(batch, 0).matrix_element)    # should print [2.43239313e-05]
```

Some terminology: An `Artifact` is the output folder of pyAmpliCol or a sub-process of MadMatrix. 
A `Provider` is a unit of computation and `Runtime` means `madspace.Runtime`. The general program
flow is `Artifact -> Provider -> Runtime`. In the previous example, we used the stock provider. Next
example shows how to generate a CPU provider using PacRunner:

```python
import pacrunner

a = pacrunner.Artifact("artifacts/zgg/")    # a pyAmpliCol artifact
process, momenta = a.validation_points()[0]
batch = momenta[None, :, :]                 # a batch of one event
provider_cpu = a.compile(device="cpu")      # PacRunner's provider on the CPU
rt_cpu = provider_cpu.runtime()             # a pacrunner.Runtime of its channel 0
print(rt_cpu(batch, 0).matrix_element)      # should print [2.43239313e-05]
```

The main change is using `a.compile(device="cpu")` instead of `a.stock()`. This function does the 
following operations:

1. Creating a folder `artifacts/.pacrunner-build/zgg/p0-cpu/`.
2. Exporting the recurrence program using `pyamplicol --export-recurrence` and saving it as `artifacts/.pacrunner-build/zgg/p0-cpu/export.json`.
3. Writing the source files for the CPU provider using `export.json` and the meta data in `artifacts/zgg`.
4. The source files are written to `artifacts/.pacrunner-build/zgg/p0-cpu/programs/0000`.
5. The source folder is compiled to generate `libumami_pac.so`.

We will discuss the files in the source folder below.

The SIMD devices build a faster CPU provider: each program becomes one symjit kernel (PacRunner's library of
the UIR operations in `pacrunner/simd/`, spliced by `codegen/compile_simd.py`), compiled by symjit's JIT for one
instruction set:

| Device | Machine | Events per kernel call (f64 / split) |
|---|---|---|
| `simd-avx2` | x86-64 with AVX2 and FMA | 4 / 8 |
| `simd-avx512` | x86-64 with AVX-512 (F, DQ) | 8 / 16 |
| `simd-neon` | aarch64 (Linux, macOS) | 2 / 4 |

`simd` is this machine's: `simd-avx512` where the CPU has AVX-512, else `simd-avx2`, and `simd-neon` on
aarch64. A SIMD device builds on a machine whose CPU runs it (symjit's JIT compiles the kernels for it), and its
library checks the CPU when it loads. PacRunner writes the machine code as object files (`pacrunner/simd/elf.py`:
an ELF object on x86-64, an assembler file on aarch64; the kernels call no functions, so they need no
relocations) and links them with the UMAMI layer. The values are the `cpu` provider's bit for bit; it needs
nothing beyond symjit and `cc`.

```python
provider_simd = a.compile(device="simd")    # PacRunner's SIMD provider on the CPU
rt_simd = provider_simd.runtime(0)
print(rt_simd(batch, 0).matrix_element)     # should print [2.43239313e-05], as the cpu provider
```

`compile(device="simd", precision="split")` (or the device names `simd-split`, `simd-avx2-split`,
`simd-avx512-split`, `simd-neon-split`) runs each program as two kernels: kernel A in f64 computes what needs
f64 from the momenta (the forms, `1/k²` of the propagators, the sources' wavefunctions, the wide parts of the
model kernels: their denominators `k² − M²`), rounded to f32; kernel B computes the rest (vertices, propagators,
model kernels, amplitudes, the reduction) in f32 at twice the lanes. Kernel B is symjit's f32 twin of its f64
kernel (`dump(.., "simd-f32")`: the machine code rewritten instruction by instruction, symjit >= 2.29.2);
`codegen/compile_split.py` splits the program. The matrix element is within about 1e-6 of f64, and 1.2–1.9×
faster than f64 on x86-64 (more with model kernels and many propagators). The precision's former name, `mixed`,
is accepted on a SIMD device.

`compile(device="cpu-jit")` is the CPU runner made by symjit instead of the C compiler: the SIMD device's kernel
of each program (the application of `simd-avx2` on x86-64, of `simd-neon` on aarch64: the same fragments,
subroutines and chained runs) as symjit's scalar code, one event per kernel call, in the same UMAMI layer. f64,
the `cpu` provider's bits; it builds where a SIMD device does. It runs fewer instructions than the C runner (no
generic `vertex()` and its dispatch) but its code is larger: on a Ryzen 9900X it is 0.8× of `cpu` for small
programs and 1.3× for large ones (`d d~ > z + 5 g`, one flow); on the M4 0.86–0.98× of `cpu`.

For now, let's continue with generating CUDA providers. 
PacRunner currently supports two types of GPU backend: `compile(device="cuda")` and `compile(device="cuda_provider")`
(also called `device="cuda_full"`: everything on the GPU). 

The first one is a hybrid provider, where the UMAMI library identifies itself as a "CPU" provider but actually runs CUDA 
kernels. The second one is a full CUDA provider that identifies itself as "CUDA".

On macOS, `compile(device="metal")` builds the same kind of hybrid provider for an Apple GPU through
Metal; it always computes in mixed precision (f32 and double-f32), since Metal has no f64. For code
that runs on both, `compile(device="gpu")` picks `metal` on macOS and `cuda` elsewhere
(`pacrunner/c/metal/PLAN.md`: the Metal runner, its tests and results).

First, the `cuda` option:

```python
import pacrunner

a = pacrunner.Artifact("artifacts/zgg/")    # a pyAmpliCol artifact
process, momenta = a.validation_points()[0]
batch = momenta[None, :, :]                 # a batch of one event, in host memory
provider_cuda = a.compile(device="cuda")    # PacRunner's provider on the GPU, called from the CPU
rt_cuda = provider_cuda.runtime()           # a pacrunner.Runtime of its channel 0
print(rt_cuda(batch, 0).matrix_element)     # should print [2.43239313e-05]
```

In this example, only the `device` option is changed. The source folder is now `artifacts/.pacrunner-build/zgg/p0-cuda/programs/0000`
and has additional files, which will be discussed below. Next, the `cuda_full` option (alias `cuda_provider`):

```python
import pacrunner
import cupy as cp

a = pacrunner.Artifact("artifacts/zgg/")    # a pyAmpliCol artifact
process, momenta = a.validation_points()[0]
batch = cp.array(momenta[None, :, :])       # a batch of one event, in GPU memory
provider_gpu = a.compile(device="cuda_full")   # PacRunner's CUDA provider (alias: "cuda_provider")
rt_gpu = provider_gpu.runtime()             # a pacrunner.Runtime of its channel 0, on a CUDA context
print(rt_gpu(batch, 0).matrix_element)      # should print [2.43239313e-05]
```

Note that for `device="cuda_full"`, we need to pass the momenta wrapped in a CuPy array.

## MadMatrix

The previous examples all used the pyAmpliCol directly to generate matrix elements. However, to find the cross-section, we need
Madspace. We start with generating the process:

```
$ mkdir -p processes
mg7> generate u u~ > z g g [amplicol]
mg7> output mg7 processes/zgg
mg7> output mg7 processes/zgg_gpu
```

`processes/` must exist: MadGraph7 creates no parent folders (it fails with a `FileNotFoundError`).
The second output, `processes/zgg_gpu`, is for the end-to-end GPU run below, which needs its own run
card.

We can load the resulting folder using `pacrunner.Output`. Each `Output` has a set of sub-processes,
which can be names using `names` or accessed using `subprocess(name)` or `subprocesses()`. Each
subprocess is a pyAmpliCol artifact with additional metadata. Therefore, we can adopt the same code
as above to generate matrix elements:

```python
import numpy as np
import pacrunner

out = pacrunner.Output("processes/zgg")
a = out.subprocess("A1_uux_zgg")

momenta = np.array([
    [500., 0., 0., 500.],
    [500., 0., 0., -500.],
    [142.22002372, -53.10090083, 59.0409804, -74.87149502],
    [380.350097, -268.20692462, 256.15852034, -84.34485361],
    [477.42987928, 321.30782545, -315.19950074, 159.21634863]])

batch = momenta[None, :, :]                 # a batch of one event
provider_cpu = a.compile(device="cpu")      # PacRunner's provider, at the param card's parameters
rt_cpu = provider_cpu.runtime()             # a pacrunner.Runtime of its channel 0
print(rt_cpu(batch, 0).matrix_element)      # should print [2.43239313e-05]
```

We can use Madspace to calculate a process cross-section:

```python
import pacrunner

out = pacrunner.Output("processes/zgg")
a = out.subprocess("A1_uux_zgg")

# the matrix elements on the GPU, MadSpace on the CPU: the output's default run card works
provider_cuda = a.compile(device="cuda")
print(provider_cuda.run().cross_section)    # should print about 75.3 (pb, ± 0.2: the default card draws a new seed each run)
```

Note that passing `cuda` uses the hybrid mode with a CPU interface; therefore, it works with the
CPU-only build of Madspace and the output's default run card. The default card draws a new random
seed for each run (`seed = -1`), so the cross section differs from run to run within its error (about
0.2 pb here); set `seed` in `Cards/run_card.toml` for a reproducible one.

We can do an end-to-end GPU run by passing `device="cuda_full"` (or its alias `"cuda_provider"`),
assuming Madspace is built for CUDA ([Installation](#installation), step 3). MadSpace then runs on the GPU too, which needs the run card's
`device = ["cuda"]`, and leading colour (`color_accuracy = "lc"`): the full-colour correction is a CPU
library. Hence the second output:

```python
import re
from pathlib import Path
import pacrunner

# everything on the GPU (MadSpace's CUDA build): the run card needs run.device = ["cuda"] and leading
# colour (the full-colour correction is a CPU library), so a second output, processes/zgg_gpu
card = Path("processes/zgg_gpu/Cards/run_card.toml")
text = re.sub(r'(?m)^device = .*$', 'device = ["cuda"]', card.read_text())
text = re.sub(r'(?m)^color_accuracy = .*$', 'color_accuracy = "lc"', text)
card.write_text(text)

out = pacrunner.Output("processes/zgg_gpu")
a = out.subprocess("A1_uux_zgg")
provider_gpu = a.compile(device="cuda_full")    # alias of "cuda_provider"
print(provider_gpu.run().cross_section)    # should print about 94.4 (pb, ± 0.2: leading colour, so above the full-colour 75.3)
```

The leading-colour cross section is larger than the full-colour one (about 94.4 against 75.5 pb for
this process): the colour approximation, not a GPU difference.

## pyAmpliCol 1.0.x: RustiCol's recurrence export

pyAmpliCol 1.0.x writes an LC artifact's programs itself: `pyamplicol export-recurrence LC_DIR -o
capture.json`; the format is its `docs/reference/recurrence-export.md`). 

## The compiled folder

| File | What it is |
| --- | --- |
| `runner.c` | the program: `int run(double *out, double *p, const double *momenta)` for one point |
| `runner.h` | its prototype and sizes: `RUNNER_LEGS`, `RUNNER_OUTPUTS`, `RUNNER_ARENA_SIZE` (the scratch `p`) |
| `pacops.c`, `pacops.h` | the sources and instructions |
| `Makefile` | `make` (`runner.o`, `pacops.o`, `testing`), `make clean`; `CC`, `CFLAGS` may be set |

With `interpreter=True`, `runner.c` holds the program as data (the encoded words, sources first, the
edge table and the tables they index, as one `uir_program`) and includes `uirvm.c`, the UIR
interpreter, copied next to it with `uirvm.h`. `run()`, `runner.h` and the values are the same, bit
for bit. The straight-line C is the CPU runner (about twice as fast); the interpreter is the GPU's,
and its CPU build is its test. The interpreter reads each row's fields straight from its word (the
`UIR_` macros of `uirvm.h`) and takes one-word rows only: a program with a wide row (an index beyond
the one-word fields) is refused.

The interpreter's `runner.c` also builds with nvcc: `make gpu` gives `runner_gpu.o` with
`int run_gpu(double *out, const double *momenta, size_t points)` (`uirvm.h`), every point on the GPU,
one thread each, momenta and outputs point by point on the host. Every function of `pacops`, `uirvm`
and the kernels is then a device function too (`PAC_FN`), and the tables are `__device__` data
(`UIR_DATA`). The outputs are the CPU build's bit for bit (`--fmad=false`, as `-ffp-contract=off`).

## Building libraries directly

`Artifact.compile` and `SubProcess.compile` export the programs and build the libraries for you. To
build from a recurrence export you already have, call `pacrunner.umami.umami_libraries`, or run it
from the command line (e.g. from another Python, such as MadGraph7's):

```sh
python -m pacrunner.umami EXPORT.json ARTIFACT/API/umami/metadata.json OUT --device cpu
python -m pacrunner.umami EXPORT.json METADATA OUT --device cuda_provider --precision mixed --cuda-arch sm_90
```

`OUT/umami_pac.json` then lists the libraries and each channel's flavours, for MadSpace;
`python -m pacrunner.umami --help` lists the options. Beneath it are the modules `pacrunner.uir` (the
export read into UIR programs, the passes, the 8-byte encoding), `pacrunner.kernels` (the symjit
kernels' MIR and their C) and `pacrunner.codegen` (a program as a compiled folder):

```python
from pacrunner import codegen, uir

programs = uir.load_recurrence_export("export.json")     # one uir.Lowered per program
codegen.compile("folder", uir.optimize(programs[0]))      # runner.c, runner.h, pacops.c, Makefile
```

Indices are 0-based throughout, and an absent one is `None`.

## Tests

```sh
python -m unittest discover -s test/python
```

Without external tools this checks the export reader, the passes, the encoding, the kernels' C and the
compiled folders against pac-julia's outputs (`test/data/goldens`, byte for byte), and, with a C
compiler, that the fixture's compiled folders pass `make test` (RustiCol's reference values, bit for
bit).
The kernels' tests need symjit ≥ 2.29. The larger golden corpus (`tools/goldens`) is used when it is
at `PACRUNNER_GOLDENS` (default `~/symjit-data/pacrunner-goldens`). More tests run when their tools are
set:

| Variable | What it enables |
| --- | --- |
| `PACRUNNER_MADGRAPH7` | a MadGraph7 checkout with MadSpace: the runtime tests |
| `PACRUNNER_TEST_ARTIFACT`, `PACRUNNER_PYAMPLICOL` | an LC artifact and the pyAmpliCol that made it: export and compile |
| `PACRUNNER_TEST_MG7_OUTPUT`, `PACRUNNER_TEST_CUDA_OUTPUT`, `PACRUNNER_TEST_MG7_MULTI` | mg7 outputs: end-to-end runs against stock |
| `PACRUNNER_TEST_TUTORIAL=1` | the tutorial's snippets (`tutorial/`), about 3 minutes |

Symbolica (pyAmpliCol) needs a writable `XDG_RUNTIME_DIR`. The scripts in `test/` (`umami_check.py`,
`umami_check_gpu.py`, `test_libraries.py`, `mg7_run.py`, ...) compare built libraries against
pyAmpliCol's stock ones through MadSpace; each says how to run it.

The C must be built with `-ffp-contract=off` (nvcc: `--fmad=false`): the values are bit for bit only
without contracted multiply-adds.
